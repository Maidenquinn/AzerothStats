# Azeroth Stats v2.0.3 — native interoperability acceptance worksheet

**Do not persist nativeRunId until this worksheet is completed in the actual game.** WoW Logs AS is optional. Use a fresh copy of the official v2.0.2 SavedVariables as the starting backup, and test with a separate v2.0.3 install. Never overwrite the only copy of player data.

## Preflight

- Record addon build/commit, game client build, OS, desktop vs browser, WoW Logs AS version, map/mode and difficulty.
- Back up `AzerothStats.lua` SavedVariables, including any automatic/manual backups; calculate file hashes before and after the test where possible.
- Confirm no Lua errors before entering the run. Keep `/azstats interop probe` output; it is diagnostic and does **not** persist the native ID.
- For each phase record a local anonymous label for the native candidate (e.g. `A`, `B`, `missing`) rather than sharing the raw identifier. Track whether it is the *same value*, not its contents.
- Note local retained run ID, run count, status, kills, duration, summary, `stats`, `equipment`, `timeline`, `deaths` presence, and WoW Logs AS gameRunId where available.

## Required scenarios

| # | Action | Observe | Expected invariant |
|---|---|---|---|
| N1 | Start and finish a normal run | Native candidate at start/mid/end; retained ID and summary | One run, no duplicate accounting |
| N2 | Start run, `/reload`, continue and finish | Candidate before/after reload; retained ID | Same run if client genuinely resumed |
| N3 | Two or more successive `/reload` in one run | Candidate after each reload; counts | No duplicate or split records |
| N4 | Finish, start new run on same map/difficulty | Native candidate old/new; local ID | Two distinct local runs; no forced native uniqueness assumption |
| N5 | Enter Endless and finish/leave | Native candidate across transitions | Correct lifecycle and duration |
| N6 | Escape → Quit game during active run, restart | Candidate, incomplete run, restored state | No fabricated victory or retrospective native ID |
| N7 | Close and restart client completely, then start new run | Candidate and old history | Historical IDs unchanged; new run not merged |

Repeat N1–N4 with both addons active and, where feasible, with WoW Logs AS disabled to confirm optional cohabitation. Record any browser-specific differences. On an ID change, reuse or absence, do **not** assign the candidate to the wrong run.

## Acceptance gates

- Seven scenarios recorded with unambiguous evidence and no uninvestigated data loss.
- Distinguish identity stability **within** a run from uniqueness **between** runs; no assumption of global uniqueness.
- Prove the observed native ID can be captured at the correct run lifecycle boundary before enabling optional persistence.
- Confirm v2.0.2 historical data and backups survive opening, restoring and closing the addon.
- For any failure: attach redacted logs, reproduce in isolation, block native persistence until fixed.

The AZST1 paste importer is not implemented by WoW Logs at the time of this worksheet; its absence is not a game-client failure.

## Observed owner test (2026-11-10)

The owner supplied two consecutive in-game exports: local IDs `azstats-320` (Naxx) and `azstats-321` (Arathi Basin) both showed the same native candidate token. Raw token omitted here. This confirms that a candidate observed in one moment cannot currently be treated as a globally unique key for retained runs. The next probe now also reports the current local run ID/status/zone beside the native candidate, allowing the owner to capture paired observations without character names. This remains diagnostic only.
