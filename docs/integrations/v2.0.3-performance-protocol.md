# v2.0.3 performance and compatibility — measurement protocol

This is a **measurement plan, not measured results**. No native client timings, heap allocations or real-save distributions have been collected. The existing synthetic regression CI is not a substitute for a v2.0.2 vs v2.0.3 performance comparison.

## Measurements required

For both official v2.0.2 and feature v2.0.3, run the same anonymized retained histories with 1, 100 and 1,000 entries; record Lua runtime (or monotonic wall clock) and memory before/after. Include sparse arrays, malformed entries, missing values, Unicode strings, quote/backslash/control characters, and realistic longest available run IDs.

Measure separately:

1. Existing startup, run collection and restore behavior — verify no new periodic work.
2. Explicit retained-run lookup by local ID (first, middle, last, missing, duplicate).
3. AZST1 serialization on v2.0.3 (v2.0.2 baseline: **not applicable**, as no AZST1 serializer existed).
4. Actual UTF-8 **byte length** of each generated code, including the six-byte `AZST1:` prefix; compare p50/p95/max.
5. Temporary allocations during export and after garbage collection, separating transient pressure from retained memory.
6. UI creation, selection and copy interaction when implemented.

Record median, p95, worst case and environment. Repeat enough times to remove first-call effects. Do not compare one cold v2.0.2 startup against a warmed v2.0.3 startup.

## Current static findings

- `ExportRetainedRunV1` performs an on-demand linear scan over `A.db.runs` using `pairs`, deliberately continuing to detect duplicate IDs across sparse indices. Expected lookup cost O(n), no persistent index.
- `ExportCodeV1` emits a fixed set of 13 metrics and 10 run fields; JSON construction is deterministic and bounded by 8,192 bytes. Escaping scans each string byte and allocates temporary fragments.
- `ExportRetainedCodeV1` projects a retained run and reprojects the safe fields before encoding. This doubles some small fixed-size work but keeps source data isolated.
- No new periodic export task or network request is introduced. The native probe reads `AZS_ZONE.run` only when invoked.
- These are **code observations**, not runtime performance claims.

## Thresholds and decisions

- Any loss of legacy fields, unexpected growth of SavedVariables, run duplication or missing backup blocks acceptance regardless of speed.
- If the 8,192-byte cap rejects legitimate data, first measure real payload distributions and UI edit-box limits; never silently truncate JSON.
- A persistent lookup index is prohibited unless measured lookup latency with 1,000 runs warrants it and its migration/restore behavior is independently proven.
- Keep raw timing reports and fixture hashes in the PR before declaring performance parity.
