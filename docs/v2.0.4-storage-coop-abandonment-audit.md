# v2.0.4 API and storage findings — 2026-11-10

## Co-op capture audit

Current implementation in `Insights.lua` consumes `AZS_PARTY` and stores sanitized party rows in each run's `coop.peers`, `coop.latest` and `coop.accounted` structures. Freshness is guarded by `AZS_PARTY_UPDATED` and the addon's party-generation counter; stale global roster data is not inherited at run start/resume.

The current observed co-op model is focused on player identity/class and combat contribution samples (damage and observed time). The inspected code does not demonstrate an API contract for other players' talent builds or equipment snapshots. The addon has a separate local-player equipment capture path in `Tracker.lua`; that is not evidence that other players' gear is exposed.

Decision:
- Do not add speculative co-op talent/equipment fields.
- Do not copy local player's equipment into peer records.
- Keep current bounded, freshness-checked co-op observations.
- Revisit only when the game exposes a documented, fresh party API for talents and equipment, with a privacy opt-in and storage budget.

## Abandoned run policy audit

Tracker explicitly distinguishes:
- `ended`: official terminal phase/result was observed.
- `interrupted`: client exit/reload or other lifecycle interruption without proof of a terminal result.
- `left`: may be an official result value when present in the game summary; it must not be inferred from every interrupted run.

Therefore a future "skip abandoned runs" feature cannot equate `interrupted` with `abandoned` or silently delete those runs. Safe initial design should be an optional history-admission policy applied only at finalization when the game explicitly reports a `left` result, with a configurable minimum duration threshold. Until exact semantics are confirmed in native tests, default remains OFF and all runs are retained. Cumulative totals, backups and existing history must not be silently rewritten.

## Storage inventory limitations

The new `/azstats storage` command reports counts and backup amplification (stored run copies), not byte sizes. WoW SavedVariables are serialized by the game client; the addon has no supported file-size API. Accurate byte measurements require inspecting the SavedVariables file outside the client or profiling representative fixtures in CI. The command deliberately does not clone, serialize or traverse every payload, avoiding extra load-time work.

Do not introduce string tables, positional statistic arrays, or compact RGB encoding until a versioned codec has:
1. Round-trip equality tests for all legacy fields and unknown extension fields.
2. v2.0.2/v2.0.3 migration and backup restore tests.
3. A rollback path preserving original roots.
4. Demonstrated material savings on real representative data.
5. A compatibility decision with WoW Logs' direct SavedVariables reader.
